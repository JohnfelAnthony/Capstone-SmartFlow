## 2. Hidden warm-up (D39)

**What happens.** On Start (Dashboard or Scenarios "Live") and on Record, `engine.start(visible + warm-up)` is followed by `engine.warm_up(w)`: the engine steps silently under the normal rules (the no-signal rule or a policy controls it when selected, as evaluation does), then `reset_metrics()` (what `tools/evaluate_controllers.py` does after `warmup_seconds`), the event log and charts are cleared, and the visible clock starts. The start request returns after the warm-up; the Dashboard shows "Preparing traffic…" in its control bar meanwhile (the Scenarios "Live" button shows it as a notice). No frames are streamed or recorded during it. Nothing is placed artificially.

**Choices I made, each recorded in D39:**
1. **Default 120 s, not 300 s.** Measured start-request time (idle machine, seed 101, fixed-time): Site A medium 0.8 s at 120 s and 2.2 s at 300 s; Site B high 4.0 s at 120 s and **43.6 s at 300 s**. My first measurements with the machine busy gave 3-8 s (Site A medium, 300 s) and 80-140 s (Site B high, 300 s): at Site B high demand vehicles build from 38 (60 s) to 138 (300 s) and each tick gets dearer. So 300 s is too slow for a click at Site B high; 120 s is about 4 s. It is one constant (`DEFAULT_RUN_WARMUP_SECONDS`) if you prefer 300 s. Training and evaluation keep their 300 s `DEFAULT_WARMUP_SECONDS`. Raw timings: [`warm-up-start-times.txt`](stage5-2026-11-07/warm-up-start-times.txt).
2. **Clock.** The engine's own clock stays absolute, exactly as in an evaluation with that warm-up. So **events, demand windows, trips and the seed are measured from the start of the simulation, warm-up included**, a closure timed inside the warm-up still applies, and the compare key (`duration_seconds` = visible + warm-up, `measurement_start` = warm-up) equals an evaluation's. What the user sees is shifted: frames, the event log and the charts carry `visible_time`, so **the visible clock starts at 0 when the warm-up ends**, and a live or recorded run stores the visible duration. Consequence to know: a closure "from 300 s" with a 120 s warm-up appears at 180 s on the visible clock. I chose this over shifting events because Compare Runs pairs recordings by that key and the owner's reference runs must equal an evaluation.
3. **Setting and old scenarios.** `engine_config.warmup_seconds` (0-3600 s, multiple of 0.1 s). A saved scenario without it **loads with the default (120), not 0**: an empty road at the start is the defect for old scenarios too, and the engine fills defaults on every load (`/api/scenarios/<id>/native-config` shows it); a scenario can save 0 to turn it off. The scenario details show it.
4. **Scripted traffic gets no warm-up** (single car, timed trips, density none without demand windows): a warm-up would play the script out unseen. The details tile says "None (the traffic is scripted)". Counts-based scenarios (density none plus windows) do get it.
5. **Recordings made this way have no warm-up frames**, so Compare Runs pairs them only with recordings made the same way (the compare key already differs by `measurement_start` and `duration_seconds`); existing recordings are untouched and I re-recorded none.
6. **The setting has no form field** (YAGNI): it is saved by the API/`engine_config` and shown on the card. Say if you want a field.

**Tests, written first** (`tests/test_hidden_warmup.py`, 9; `src/api/native-scenario.test.ts`, 2): they first failed on the missing `warm_up` and `DEFAULT_RUN_WARMUP_SECONDS` (import errors), then passed. Metrics exclude the warm-up (`measurement_start` = warm-up, throughput 0 at the first frame, charts and events start at 0); the first frame has vehicles at medium demand; a hidden-warm-up run equals the by-hand evaluation sequence tick for tick (metrics and vehicle records) and is reproducible; a closure inside the warm-up applies and one timed 10 s into the visible run closes at visible 10 s; the no-signal rule controls the warm-up; bad values are refused; an old scenario resolves with the default; a live start through the API returns at clock 0 with vehicles, the full visible duration and the visible duration stored; a recording starts at time 0 with 51 frames and the compare key of a 40 s warm-up plus 5 s run. Browser check: the Dashboard control bar showed "Preparing traffic…" during Start (read from the page text; I did not manage to catch it in a screenshot) and the run opened with vehicles already on the road at 00:03 ([`live-run-first-seconds-after-warm-up.jpg`](stage5-2026-11-07/live-run-first-seconds-after-warm-up.jpg)).

- Frames during the warm-up are not saved anywhere, so a live run cannot be rewound into it.
- The 18 hidden models are not confirmed against the owner's database; the rule is the page's `compatible` flag and checkpoints.
- Counts-based scenario cards show "Traffic density: None" (the counts set it so); misleading, not changed.
- The run-report CSV mixes local "Started" and UTC "Ended" timestamps (pre-existing, not touched).
- I did not run the real Field Observer GUI export (still open from stage 4) and ran no long training.
- **Slip:** I once started the API server without the scratch environment variables for a few seconds; it created a fresh, empty `data/smartflow.db` inside this worktree (git-ignored, birth time that minute, 2 seeded scenarios, 0 runs). I deleted that file. The owner's database in the main checkout (last modified 5 November) was not touched, and no server was ever pointed at it.
