## 1. Problem framing and open questions

### Problem, users and critical workflow

SmartFlow must become a defensible capstone system for testing traffic signals and adaptive routes in a bounded Tagum study area. The engine, UI, learning and reporting workflow has dated synthetic acceptance. The remaining research challenge is to establish representative inputs and baseline fidelity, then complete independent validation and fair controller/routing comparisons within the confirmed academic schedule.

Researchers need reproducible experiments; traffic/planning reviewers and panel members need understandable evidence; administrators need access control and preserved results. These audiences do not imply that each has a separately implemented account role.

The critical workflow is **select verified network → save complete inputs → run a baseline → run a compatible policy on matched demand → inspect traffic → save/replay → compare/export → explain results and assumptions**. Training supports this workflow; a training button alone is not the product outcome.

The research question is whether the tested strategies improve selected traffic outcomes under stated conditions. A positive result is not guaranteed. The system must report negative or inconclusive results honestly.

### Scope, non-goals and definition of done

The agreed scope is React, custom Python traffic logic, dynamic connected-road visualization, configurable demand/signals/disruptions, separate adaptive routing, RL signal evaluation and saved evidence. The supplied network contains five junctions, twelve road segments and twenty-four directed lanes. The initial single-car demonstration remains available; the implemented shared 2D/3D scene also supports mixed traffic, pedestrians, inspection and analytical overlays.

Do not spend this release on decorative scenery, a citywide road editor, a second desktop implementation, live CCTV/GPS/IoT ingestion or physical signal control. Map import does not automatically produce a calibrated traffic model.

**Provisional release assumption:** evaluate one RL-controlled junction within the connected five-junction network, with specified control at the others. This matches the current environment. It is **not yet an agreed academic requirement**. If the panel requires every junction to be adaptive or coordinated, revise the scope and plan explicitly; single-junction tests cannot satisfy it.

### Challenge to the current proposal

1. **Removing SUMO transfers traffic-model responsibility to this project.** Passing safety tests can coexist with unrealistic junction capacity or travel times. Junction occupancy was one vehicle at a time until October 25, 2026 (about 456 veh/h/lane); approach-scoped occupancy now discharges a synthetic through movement at about 1,480 veh/h/lane, but that is a plausibility check, not calibration against Tagum discharge headways.
2. **Map automation was not uniquely enabled by removing SUMO.** SUMO supports native OSM import and scenario-generation tooling. The defensible rationale is implementation control and fit with the selected stack, not impossibility of connected OSM roads in SUMO. This correction does not reverse the user's removal decision. [SUMO OSM import](https://sumo.dlr.de/docs/Networks/Import/OpenStreetMap.html).
3. **RL can exploit a simulator's shortcuts.** Reward improvements require field plausibility, a fair baseline, matched demand and held-out evaluation before being interpreted as traffic improvements.
4. **The configuration contract remains essential.** Browser editing/model selection and saved native settings now have dated acceptance; preserve that contract when extending the engine or adding algorithms.
5. **Existing effort does not justify ignoring failure.** If the early validity gate fails, reconsider the model or obtain an explicit scope decision. Additional visual polish cannot resolve a research blocker.

## 4. Architecture and delivery plan

**D25 — minimal map with junction column, October 25:** supersedes D24's map chrome. Following the owner-approved [dashboard redesign plan](DASHBOARD_REDESIGN_PLAN_2026-10-25.md), the map shows only three corner chips (intersection, signal phase, phase timer), zoom controls and clickable J-tags in both 2D and 3D. The control bar sits under the map; the idle setup card (New run / Replay recording) replaces the Setup sheet. A right column holds the network map, the selected-junction card (photo, Signal phases / Queue info / Performance tabs) and a Signal control card that enables QL/DQL/PPO only when a compatible trained model exists for the controlled junction. Tabs show only engine-measured per-junction values (services from `phase_order`, lane queues, vehicle passages, waiting pedestrians, vehicle-weighted incoming speed); network-wide wait, throughput and travel time stay in the KPI row. The junction photo is a labelled CC BY 3.0 placeholder from a Davao intersection until field photos named `J1.jpg` / `J2.jpg` are added under `public/assets/junctions/`.

**D26 — single `native-5` engine bump, October 26:** every engine-behaviour change from the [engine fix plan](ENGINE_FIX_PLAN_2026-10-25.md) so far (P0-1 deadlock, P1-2 step 1 capacity, P1-4 maximum red, P1-3 shared pedestrian rule, per-junction stopped seconds) ships under one engine ID, `native-5`. The observation (`native-local-22-v2`) and action (`protected-service-5-v1`) contracts are unchanged, but the model contract includes the engine ID, so `native-4` models, recordings and metric readings become history; they are kept, not relabelled. The dashboard's fixed-time baseline now requires a saved run whose engine version equals the current metric catalog's, so a run without an engine version or from an older engine is never used for the % comparison.

**D27 — local per-interval reward `reward_v3`, October 26:** engine fix plan P1-5. The training reward no longer reads network-wide running averages. Per decision interval Δt at the controlled junction: + 0.5 × vehicles discharged ÷ (Δt / 2.0 s saturation headway), − 1.0 × mean stopped vehicles per approach (Δ stopped vehicle-seconds ÷ Δt ÷ 4) ÷ 30, − 0.5 × longest approach queue ÷ 30, − 0.25 × waiting pedestrians ÷ 20, − 0.05 per phase switch; each normalised term is clamped to [0, 1] and the scales come from `rl_state.py`. The running maximum queue term was removed. The reported KPIs stay network-wide plus J1-local delay, so the reward and the evaluation measure different things on purpose. `REWARD_VERSION` lives in `simulation/rl_reward.py` and DQL, PPO and QL training metadata all read it. The observation (`obs_v2`, including its whole-trip per-approach wait) is unchanged.

**D28 — default RL training budget, October 26:** engine fix plan P1-7. A training run now defaults to 560 episodes of 900 s after a 300 s warmup at 5 s decisions, about 101,000 decisions, so each episode starts from developed traffic instead of a near-empty network (previously 10 episodes of 300 s after 20 s: 610 decisions). The three values are defined once in `simulation/rl_env.py` (`DEFAULT_TRAINING_EPISODES`, `DEFAULT_WARMUP_SECONDS`, `DEFAULT_EPISODE_SECONDS`) and read by the environment, the API settings, the training service, the QL/DQL/PPO trainers and the controller evaluation; the web form mirrors them. **D30 — two-site study: separate site networks, `first_come`, no-signal control, grouped phases, contract v4 and `native-7`, October 31 – November 1:** the study compares today's unsignalized condition (the only one a video can validate) with a proposed fixed-time signal and a proposed RL signal, per [the two-site plan](superpowers/plans/2026-10-31-two-site-study.md). Decisions: (1) each site is its own single-junction network (`data/networks/tagum_site_{a,b}.json`, built from OpenStreetMap, unverified in the field) and each scenario names its network and fingerprint; (2) junction mode `first_come` admits vehicles by arrival order at an approach zone, and the run-level `no-signal` controller applies it to every junction without touching the saved scenario; its approach speed, zone length, turn speed and class speed factors are per-site `engine_config.site_calibration`, never edits of shared constants; (3) `phase_order` may group approaches that share a green, `phase_greens` gives each phase its own green, and a provisional Webster calculator proposes plans (placeholder passenger-car equivalents and saturation flows until cited); (4) RL serves phase slots under `native-local-20-v4` / `phase-service-5-v2`, and every model stores the `phase_plan` its actions mean; (5) training or final evaluation of a study site needs a current, independent PASS from `services/site_validation.py` for the identical physical model, protocol and criteria (design 0.15), enforced in the API and the command-line tools; `--synthetic-smoke-test` runs a code check that marks its artifact. **Compatibility:** the first-come work did not change signalized or all-way-stop traffic: same-seed state digests on the five- and two-junction networks and on the synthetic cross equal the pre-two-site `native-6` code (pinned in `tests/test_native6_compat.py`). The engine still moved to `native-7` once, with the new RL contract, so that no run, recording or model made under one contract can be read as the other. `native-6` models and recordings are refused with the existing "train a new model" / "generate a new recording" messages and are kept as history, not relabelled; dashboard baselines and the stored `native-6` reference runs must be re-recorded on `native-7` (`tools/record_fixed_time_baselines.py`, which needs the owner's approval to write the database). A study site's `native-6` pass, if any existed, would be stale by design (the engine content hash is part of its identity). **Limits:** software readiness is not field validity. The site geometry, the first-come assumption, the approach zone and speeds, the class mapping, the initialization and every threshold are provisional until the team's reviewed observations and a frozen, adviser-agreed criteria file exist.

**D29 — mixed-traffic sub-lane model, `native-6`, October 28:** implements the owner-approved [mixed-traffic design](superpowers/specs/2026-10-26-mixed-traffic-design.md) through the [mixed-traffic plan](superpowers/plans/2026-10-26-mixed-traffic.md). Each direction of a road keeps its real width as one modeled lane; every vehicle has a sideways position and, while turning sideways, a capped drawn angle. Vehicles follow only what overlaps their sideways band, so vehicles travel and queue side by side. Motorcycles seek gaps and filter to the stop line; cars, buses and trucks keep to the centre-line side of their lane portion and tricycles to the kerb, and those classes move sideways only while moving forward. Vehicles enter a junction connector at their real sideways position; merging or crossing movements from one approach follow a fixed order, and a committed vehicle's remaining swept path is kept clear by every other vehicle, including followers on its own approach. A sideways move stops `ALONGSIDE_GAP_M` (0.05 m) short of a neighbour, because lateral bands are lane coordinates and bodies straddling a polyline bend sit slightly rotated against each other. Each driver draws speed and headway multipliers from a separate random stream (`DRIVER_STREAM_SALT`), so arrivals and pedestrians match `native-5` for a seed. The `tagum_provisional` mix (motorcycle 0.55, tricycle 0.25, car 0.15, truck 0.03, bus 0.02) and the class parameters in `simulation/mixed_traffic.py` are **provisional, uncalibrated values**; calibration waits for confirmed sites and reviewed Field Observer counts. Accepted limitation: exit storage still counts vehicles end to end, so a road backed up with vehicles side by side counts as full earlier than it is. Because the Tagum mix queues reach a per-approach p95 of 62 vehicles, the observation's queue and active-vehicle scales are 70 (`obs_v3`, `native-local-22-v3`, `reward_v4`). `native-5` models, recordings and metric readings become history; they are kept, not relabelled. Acceptance (1800 s, seeds 101/102, 20 cases) is in [the report](reports/mixed-traffic-acceptance.json).

**D24 — LGU-facing dashboard and provisional two-junction site, October 24:** the primary audience is an LGU traffic administrator, so the Dashboard is one shadcn layout: four KPI cards (average wait, average queue, completed-trip rate, completed trips) with a percentage change against the latest completed fixed-time run of the same scenario and seed; the map with a junction panel (current service, timer and waiting vehicles per approach labelled by compass side with clear/low/moderate/high bands); one control bar (Live/Replay, start/pause/stop, speed, Setup sheet); and a collapsible trend chart. 2D is the primary view and 3D an optional illustrative view with regular set-back blocks. The sidebar groups Operate, Research and Admin pages. The final two study intersections are not yet confirmed; `data/networks/tagum_network_2j.json` (J1 Arellano/Osmeña and J2 Mabini/Osmeña, built by `tools/build_study_network.py --junctions`) is a provisional placeholder selected with `SMARTFLOW_NETWORK_PATH` and an isolated database. It keeps the `tagum_network` id because RL state encodes that id; the five-junction file remains the default. Swapping in the final site means regenerating that file, not changing the UI.

**D23 — result interpretation, October 24:** `simulation/metric_definitions.json` is the versioned native metric catalog shared by Python reporting/calibration and TypeScript Help/live/saved/comparison views. `services/metric_definitions.py` and `src/lib/metrics.ts` interpret availability without changing stored numeric evidence: missing/non-finite values, empty/unrecorded average populations, unsampled queues and zero-duration rates are unavailable. Explicitly different historical engines are not assigned current native meanings. `/api/metrics/definitions` exposes the same catalog to authenticated clients. New exports retain raw metrics and add definitions/version and missing-value reasons; calibration records retain their frozen definitions and new records identify the catalog version. Original artifacts and older frozen fit records are not rewritten.

Controller summaries retain each repetition, available/total counts and unweighted per-run mean/min/max/population standard deviation; unavailable averages are excluded and incomplete wait coverage is not ranked. The score remains negative mean stopped vehicle wait. `waiting_time_rank` orders that mean with completed trips as the tie-breaker, uses shared ranks for ties and leaves unavailable cases unranked. `traffic_performance_rank` remains an explicitly labeled legacy alias. New summaries carry a criterion/version, per-metric differences and zero-reference percentage unavailability, and `overall_recommendation: null`; no weighted score or acceptable-degradation rule is invented. Standard deviation is not a confidence interval. At this interpretation checkpoint the only engine addition was an active-emergency population counter; the subsequent ordinary-traffic scope decision above removes that counter and its metrics, advances native compatibility and leaves the ordinary traffic mathematics intact.

### Native model reference

- **Time:** `native-6`, 0.1-second steps, metres/seconds/m/s. Start/reset restores baseline constraints before replaying events. Version changes intentionally invalidate incompatible model/recording artifacts.
- **Graph:** five junctions, twelve roads, twenty-four directed lanes, covering parts of Arellano, Jose Abad Santos, Lapu-Lapu, Mabini and Osmeña streets. - **Vehicles:** IDM-style following plus hard gaps; car, motorcycle, tricycle, bus and truck dimensions/speed factors. This does not imply lane changing, overtaking or motorcycle filtering.
- **Junctions:** exclusive reservations, signal/stop permission, downstream storage and pedestrian clearance. Simplified all-way-stop comparison exists. Since October 25, 2026, occupancy is approach-scoped at signalized junctions (vehicles from the approach with green may be inside together; others and pedestrians wait until it is empty) with a lane-storage entry rule; all-way stops keep one vehicle. Synthetic saturation headways (`tests/test_junction_capacity.py`) need field calibration.
- **Signals:** phase order/timing/offset, green limits, yellow/all-red, pedestrian service through safety rules. Log safety overrides separately from learned decisions.
- **Routing:** travel-time/queue costs; avoids closed/prohibited movements. Default reroute interval is 15 seconds with a 15% improvement threshold. `static` suppresses congestion rerouting but still permits closure detours.
- **Demand:** single-car replacement is a demonstration, not a matched-arrival comparison. Seeded schedules/windows and explicit trips supply experiments. Blocked arrivals wait subject to reported capacity limits; crossing distance/speed and pedestrian waiting threshold are configurable.
- **RL:** 22 continuous observation values, 15 tabular-state components, five service actions, one selected junction. Metadata identifies `native-local-22-v3`, `obs_v3`, `reward_v4`, `protected-service-5-v1` and the default network fingerprint. The reward (`reward_v4`, the `reward_v3` terms at the `obs_v3` queue scale) uses only the controlled junction over the last decision interval: vehicles discharged, stopped vehicle-seconds, longest approach queue, waiting pedestrians and phase switches. Compatibility metadata alone does not establish artifact trust.

### Operating design and cost controls

For the first trial, use one persistent API process, explicit live-run ownership, persistent SQLite/artifact storage and HTTPS. Keep substantial training separate. Redis, Kubernetes, distributed simulation and a replacement database are not justified by current demonstrated requirements.

The current runtime claims one authenticated operator for configure, lifecycle, playback and speed changes. Other users can view its state but receive a conflict on mutation; reset releases the claim, and an administrator can explicitly take over. This claim is in process memory, so deployment must stay at one API worker until ownership and runtime state move to a shared store. CSV imports validate complete candidate settings before preserving source bytes or saving a scenario. Count bins become evenly spaced synthetic arrivals; turn rows identify a permitted junction movement on their supplied boundary route, while later adaptive rerouting can change the actual movement. Source hash, date, network hash and conversion are kept with demand provenance. Comparison/export keys and reports retain model, seed, engine, network and demand identity and show unfinished demand.

FastAPI documents that separate worker processes normally have separate memory. Applied to this repository's singleton engine, multiple workers would create separate runtimes, not a shared simulation. This is an inference from that process model and current source. [FastAPI deployment concepts](https://fastapi.tiangolo.com/deployment/concepts/).

No hosting price can be responsibly selected without a provider, region, budget and measured workload. Measure CPU/RAM, step/frame time, recording growth and training wall time. Budget for API uptime, storage, backups, bandwidth and any approved training compute. Recording volume is approximately `recorded frames × average bytes per frame × retained runs`, adjusted using measured compression. Independent concurrent runs, rather than registered account count, are the immediate compute scaling issue.

### Evaluation protocol to settle with the adviser

Use ordinary, peak and disruption/recovery scenarios with the same frozen graph, exogenous arrivals, vehicle mix, pedestrian demand, warmup, duration and safety rules for each controller comparison. Include a credible fixed-time baseline. Use a separate static-versus-adaptive routing comparison, or a clearly labeled factorial experiment, so signal and routing effects are not confused.

Start planning with at least five held-out demand seeds per condition; this is a practical starting allocation, not a claim of statistical sufficiency. Decide repetitions from variability, available time and the agreed protocol. Use multiple training seeds when making claims about an algorithm rather than one trained artifact. Report per-run results and paired differences with an appropriate uncertainty estimate; retain failures and negative results. Do not tune on the held-out evaluation set or report only the best seed. If resources limit repetitions, state that limitation instead of overstating confidence.

Verify custom-environment behavior, separate evaluation from training, and distinguish time-limit truncation from natural termination. These checks and repeated evaluation follow the general guidance in the [Stable-Baselines3 RL tips](https://stable-baselines3.readthedocs.io/en/master/guide/rl_tips.html); they do not establish SmartFlow model validity or mandate a dependency upgrade.

### Rollback and evidence recovery

Before schema or artifact-layout changes, stop new writes/jobs and create a coherent checkpoint of the database, recordings, models, graph and manifests. Use SQLite's supported backup mechanism or a cleanly closed database snapshot; copying an actively changing database file alone is not a recovery plan. See the [SQLite Online Backup API](https://sqlite.org/backup.html).

The September 27 API bundle uses SQLite's backup API and checks references before success. It stages a verified ZIP under the database storage directory's `backups/restores/`, rewrites artifact paths, invalidates copied sessions and writes `restore_environment.json`. Launch a separate API process with its staged `SMARTFLOW_DB_PATH` and `SMARTFLOW_NETWORK_PATH`, plus a fresh secret key. Legacy `.db` files stage without artifacts and cannot certify model or replay recovery. Do not point production at a staged copy until its scenario/model/replay and role workflows have been inspected. Do not replace the live database while the process-local simulation or worker is running.

Test restoration in a separate location and confirm that database references resolve to the restored files and that a saved run can be replayed. Keep a last-known-working source/build and a matching data/artifact checkpoint. Revert them together when compatibility requires it; a code-only rollback may not undo a schema or model-contract change.

After a failed release, stop admission of new runs, preserve diagnostic logs and failed artifacts, restore the compatible checkpoint, and repeat a baseline/replay smoke check. Mark interrupted jobs explicitly. Do not promise exact simulation resumption after a crash unless that capability has been implemented and tested.
