# Single-host deployment package

This package is for a **bounded single-operator trial**. The API's live and training state lives in one Python process. Run one Uvicorn worker, keep long training offline, and do not claim capacity for concurrent independent runs. No provider or public hostname is selected here.

## Prepare

1. Copy the complete SmartFlow source and retained `data/networks/`, `data/scenarios/`, `docs/research_sources/`, saved database/artifacts and any required ignored research evidence. Keep a coherent ZIP backup from the admin page before changing a running installation.
2. Recreate `.venv` and run `npm ci`, `npm run venv:install`, `.venv/Scripts/python.exe -m pip install -r requirements-dev.txt`, the Python suite, `npm run check:api` and `npm run build` from the new root. Do not move a Windows virtual environment unchanged. Review `npm audit` output before publication; the September 27 production-only audit was clean, while the full build-tool audit still reported advisories. A passing build is not a security clearance.
3. Provide the settings in [production.env.example](production.env.example) through the host's secret/environment manager. Generate a fresh, private secret. Use an HTTPS public origin. Store SQLite, recordings, model and job files on persistent storage with at least 3 GiB initially free for the default one-hour recording cap; set permissions so only the API account can write them. A shorter cap can lower that requirement. Check disk growth against the measured 139.3 MiB raw and 24.6 MiB gzip per five-minute Very High synthetic recording and bundle retention. Keep a separate off-host copy of backups.
4. Terminate HTTPS at a reverse proxy on the same origin that serves `dist/`, forwards `/api/*` and `/ws/*` to `127.0.0.1:8000`, and supports WebSocket upgrades. Configure HTTPS and HTTP-to-HTTPS redirect there. Keep port 8000 loopback-only. The production build uses the page's HTTPS origin by default; set `VITE_SMARTFLOW_API_BASE_URL` during build if the API uses a different approved origin. Set `SMARTFLOW_ALLOWED_ORIGINS` to the exact browser origin(s), without wildcards. The API also rejects foreign WebSocket origins.
5. Run [start-api.ps1](start-api.ps1) under a supervised service account, then check `/api/health`, login, scenario configure/start/stop, recording/replay and report export through the HTTPS origin. The script runs preflight and exactly one worker. Persist API logs without session tokens or credentials. Restrict administrative access and registration.

## Operation and recovery

- The API now atomically admits one compute workload across live simulation, training/evaluation and recording. Conflicts return HTTP 409 before run/job allocation. Paused live runs retain admission; stop/reset, completion and worker failure release it, while cancellation releases only after the worker exits. Replay reads saved frames without a compute lease. This guard is process-local: keep one API worker and schedule independent CLI jobs offline. Recording still enforces a default 3,600-second duration limit (`SMARTFLOW_MAX_RECORDING_SECONDS`) and a free-space reserve based on requested duration; admission does not replace disk monitoring or retention. Watch run/job status, stream reconnections, p95 step/frame cost, render fps, unfinished demand, free disk and backup age. The September 27 desktop measurements in [progress](../docs/PROGRESS_AND_HANDOFF.md) are a starting estimate, not target-host certification. Re-measure on the host and with expected viewers before widening the trial.
- Schedule backups while no live run, recording or training job is active. Download the ZIP and rehearse **Verify restore** in a separate directory. Inspect the staged `restore_environment.json`, use a new secret, then verify scenario/model/replay and roles through a separate API. A legacy `.db` export omits artifacts.
- On process failure, preserve logs and partial artifacts. Restart the one API worker; startup reconciles orphaned runs and jobs. The browser shows the disconnection and can start a new run after reconnect. There is no exact mid-run resumption.
- For rollback, retain the last working source/build with its matching backup bundle. Stop writes, stage and verify that bundle, then point a single worker at the verified copy. Test login, baseline and replay before opening access again. Do not roll back code alone across incompatible schema/model contracts.
- For an offline demonstration, use `npm run api` and `npm run dev` on the local machine with an isolated demo database and a pre-recorded replay. This is a fallback, not a production HTTPS setup.

External publication, provider purchase, real-data claims and traffic-control use require separate project decisions and evidence.
